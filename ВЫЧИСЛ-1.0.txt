================================================================================
ТЕОРЕТИЧЕСКОЕ ОСНОВАНИЕ
================================================================================

Модуль вводится для закрытия выявленной лакуны: в МФО-НС-13.3.3 системно присутствует эпистемический provenance и функционально присутствуют элементы материально-практического provenance, однако отсутствует самостоятельная системная формализация вычислительно-исполнительного provenance.

Цепочка, подлежащая фиксации при срабатывании триггера:

DATA → CODE → EXECUTION → ARTIFACT → ENVIRONMENT

Модуль является условным. Его отсутствие не блокирует ответ (Императив 2), а только маркирует результат.

================================================================================
ТРИГГЕР АКТИВАЦИИ
================================================================================

Модуль активируется, если в ответе присутствуют результаты, полученные через:

1. Исполнение кода (скрипты, notebooks, программы);
2. Численное моделирование или симуляцию;
3. Автоматизированную обработку данных с генерацией таблиц, графиков, метрик;
4. Иные вычислительные процедуры, где изменение окружения или версий библиотек может изменить результат (зависимость от конкретного исполнения).

Модуль НЕ активируется для:
- простых арифметических расчётов по явным формулам из атрибутированных данных (покрыто протоколом РРИ-04, п. 6.15);
- чисто текстовых, нормативных, исторических, философских или логических задач.

================================================================================
МИНИМАЛЬНЫЙ ОБЯЗАТЕЛЬНЫЙ КОНТУР
================================================================================

При активации модуля система обязана зафиксировать:

| Компонент                              | Требование                                                                 | Формат                                      |
|----------------------------------------|----------------------------------------------------------------------------|---------------------------------------------|
| Метод / код                            | Описание использованного метода или ссылка на код (или его хеш)           | Текстовое описание + (опционально) ссылка   |
| Ключевые параметры и входные данные    | Основные параметры и входные данные, влияющие на результат                 | Таблица или структурированное описание     |
| Окружение                              | Версии основных библиотек / runtime или явное указание «окружение не зафиксировано» | Список зависимостей с версиями либо фраза «не зафиксировано» |
| Статус воспроизводимости               | Возможность повторного запуска                                             | «обеспечена» / «частично» / «не обеспечена» |

Отсутствие любого компонента не блокирует ответ, но отражается в диагностическом флаге.

СЛОВАРНОЕ ДОПОЛНЕНИЕ ВЫЧИСЛ-1
================================================================================

Новые предметные области:

| Область       | Содержание                          | Переменные |
|---------------|-------------------------------------|------------|
| COMP_ENV      | Окружение выполнения                | env        |
| COMP_EXEC     | Исполнение (запуск, логи)           | exec       |
| COMP_ARTIFACT | Вычислительные артефакты            | art        |

Новые предикаты:

| Предикат                        | Определение                                                                 |
|---------------------------------|-----------------------------------------------------------------------------|
| CodeUsed(m, a)                  | Метод/код m использован для получения артефакта a (m ∈ METHOD, a ∈ COMP_ARTIFACT) |
| EnvironmentSnapshot(env, a)     | Окружение env зафиксировано для артефакта a (env ∈ COMP_ENV, a ∈ COMP_ARTIFACT) |
| ExecutionLog(exec, a)           | Журнал исполнения exec зафиксирован для артефакта a (exec ∈ COMP_EXEC, a ∈ COMP_ARTIFACT) |
| Reproducible(a)                 | Артефакт a воспроизводим (a ∈ COMP_ARTIFACT)                                |
| DependsOnExecution(a)           | Результат артефакта a зависит от конкретного исполнения (a ∈ COMP_ARTIFACT) |
| ExecutionProvenanceMissing(a)   | Для артефакта a отсутствует минимальный контур вычислительного provenance (a ∈ COMP_ARTIFACT) |

================================================================================
МОДИФИКАЦИИ СУЩЕСТВУЮЩИХ ПРОТОКОЛОВ
================================================================================

1. ПМПВ (п. 6.5)
Добавляется опциональный этап 8 (только при активации модуля):

Этап 8. Фиксация вычислительного происхождения.
Если результат получен через вычислительную процедуру (триггер модуля ВЫЧИСЛ-1.0), система обязана зафиксировать минимальный контур. Отсутствие фиксации маркируется флагом [EXECUTION_PROVENANCE_MISSING].

2. ТАД (Приложение 1)
Траектория расширяется опциональной осью:
T = {Q, S, E, C, A_c}, где A_c — множество вычислительных артефактов.

3. Закон II.22 (практика)
Добавляется уточнение:

Для вычислительных результатов практическая верификация включает, где это возможно, воспроизводимость расчёта или моделирования. Отсутствие такой воспроизводимости не отменяет практической значимости результата, но маркируется диагностическим флагом [EXECUTION_PROVENANCE_MISSING] и требует отдельного обоснования.

4. Граница с РРИ-04 (п. 6.15)
- РРИ-04 — простые расчёты по явным формулам.
- ВЫЧИСЛ-1.0 — процедуры, зависящие от исполнения (код, моделирование, обработка данных и т.п.).

================================================================================
ГРАНИЦЫ ПРИМЕНИМОСТИ
================================================================================

Действительно:
- Для ответов, содержащих вычислительные результаты, зависящие от исполнения.
- В статусе экспериментальной надстройки до калибровки.

Запрещено:
- Применять при отсутствии триггера.
- Превращать флаг в числовой множитель КК_итог.
- Блокировать ответ из-за отсутствия provenance.
- Сливать вычислительный контур с эпистемическим или материально-практическим в единую жёсткую цепочку.

Модуль не заменяет и не отменяет существующие протоколы (РРИ-04, ПМПВ и др.), а дополняет их опциональным слоем.

После калибровки по п. 6.9 возможны три исхода:
1. Интеграция в ядро (с понижением статуса).
2. Сохранение как экспериментальной надстройки.
3. Свёртывание до минимального варианта (только флаг + примечание в ПМПВ).
