РАЗДЕЛ 0. КРИТИЧЕСКИЕ ИМПЕРАТИВЫ — НЕ ПОДЛЕЖАТ НАРУШЕНИЮ

ИМПЕРАТИВ 1 · ОБЯЗАТЕЛЬНОЕ ЧТЕНИЕ ИНСТРУКЦИЙ ПРИ ИМПОРТЕ

При получении JSON-файла графа ты ОБЯЗАН сначала прочитать ВСЕ элементы массива operator_instructions и ВСЕ поля comment каждого узла.

ЗАПРЕЩЕНО игнорировать массив operator_instructions.

ЗАПРЕЩЕНО игнорировать поле comment любого узла.

ЗАПРЕЩЕНО отображать старый граф без обработки инструкций.

ИМПЕРАТИВ 2 · ОБЯЗАТЕЛЬНОЕ ПРИМЕНЕНИЕ УКАЗАННЫХ ЛОГИК

Если узел типа LOGIC_OPERATION имеет used: false И его поле comment содержит указание применить (слова «применить», «примени», «подключи», «используй», «активируй», «добавь» на любом языке), ты ОБЯЗАН:

1. Изменить used на true в НОВОМ графе.

2. Изменить цвет узла с серого (#444455) на зелёный (#60ff90).

3. Добавить связи (edges) от утверждений (CLAIM) к данной логике и от данной логики к результату (RESULT).

4. Добавить описание применения логики в поле desc.

ИМПЕРАТИВ 3 · ОБЯЗАТЕЛЬНАЯ ГЕНЕРАЦИЯ НОВОГО ГРАФА

Ты ОБЯЗАН сгенерировать НОВЫЙ граф с изменённым составом логик. НОВЫЙ граф отличается от старого:

1. Содержит ВСЕ логики, указанные в инструкциях как «применить».

2. Каждая новая логика имеет связи с другими узлами.

3. Каждая новая логика имеет описание применения.

ЗАПРЕЩЕНО повторно генерировать тот же граф без изменений.

ЗАПРЕЩЕНО игнорировать инструкции оператора и оставлять состав логик прежним.

ИМПЕРАТИВ 4 · ОБЯЗАТЕЛЬНЫЕ СВЯЗИ ДЛЯ КАЖДОЙ ЛОГИКИ

Каждая применённая логика (used: true) ОБЯЗАНА иметь минимум 2 связи:

1. Входящую связь от утверждения (CLAIM) или evidence (EVIDENCE) с типом ACTIVATES или INPUT.

2. Исходящую связь к результату (RESULT) или критерию (CRITERION) с типом FEEDS или DERIVES или VALIDATES.

ЗАПРЕЩЕНО создавать узел логики без связей.

ИМПЕРАТИВ 5 · ОБЯЗАТЕЛЬНАЯ ПОЛНАЯ ИНФОРМАЦИЯ В ПАНЕЛИ УЗЛА

При клике на узел панель ОБЯЗАНА показывать:

1. Название узла (name)

2. Тип узла (type)

3. Полное описание (desc)

4. ID узла

5. Статус (ok / fail / pending)

6. Комментарий оператора (comment)

7. Количество входящих связей

8. Количество исходящих связей

9. Трассировку (прослеживается ли до источника)

10. Поле для ввода нового комментария

ЗАПРЕЩЕНО показывать панель узла без описания или без комментария.

ИМПЕРАТИВ 6 · ОБЯЗАТЕЛЬНЫЙ РЕЖИМ ВЫДЕЛЕНИЯ

Ты ОБЯЗАН реализовать режим выделения узлов:

1. Кнопка или чекбокс «Режим выделения» в панели управления.

2. При включённом режиме клик по узлу добавляет/убирает его из выделения.

3. Выделенные узлы подсвечиваются жёлтым кольцом.

4. Кнопка «Создать инструкцию» активна только при выделенных узлах.

5. Модальное окно с textarea для текста инструкции и выбором приоритета (HIGH/MEDIUM/LOW).

6. Панель «Инструкции для следующего цикла» со списком созданных инструкций.

ЗАПРЕЩЕНО создавать 3Д-файл без режима выделения и создания инструкций.

ИМПЕРАТИВ 7 · КЛАВИАТУРА

Авто-вращение управляется клавишей Page Up.

ЗАПРЕЩЕНО использовать клавишу Пробел (Space) для управления вращением. Пробел нужен для ввода текста.

В обработчике клавиатуры ОБЯЗАТЕЛЬНА проверка: если фокус на textarea или input — НЕ обрабатывать горячие клавиши.

РАЗДЕЛ 1. АЛГОРИТМ ОБРАБОТКИ ИМПОРТИРОВАННОГО JSON — ОБЯЗАТЕЛЕН К ИСПОЛНЕНИЮ

Когда ты получаешь JSON-файл графа (от пользователя или через импорт), ты ОБЯЗАН выполнить следующие шаги ПО ПОРЯДКУ:

ШАГ 1. ПРОЧИТАЙ ВЕСЬ JSON

Прочитай корневой объект. Проверь поля: protocol (должен быть "TAD-3D-VR"), version, graph, operator_instructions.

ШАГ 2. ИЗВЛЕКИ ИНСТРУКЦИИ ОПЕРАТОРА

Прочитай массив operator_instructions. Для каждой инструкции зафиксируй:

  • id — идентификатор
  • target_nodes — целевые узлы
  • instruction — текст инструкции
  • priority — приоритет (HIGH / MEDIUM / LOW)

Если массив пуст или отсутствует — переходи к Шагу 4.

Если массив не пуст — ты ОБЯЗАН обработать каждую инструкцию.

ШАГ 3. ПРОВЕРЬ КОММЕНТАРИИ КАЖДОГО УЗЛА

Для КАЖДОГО узла в массиве graph.nodes проверь поле comment.

Если comment содержит слова: «применить», «примени», «подключи», «используй», «активируй», «добавь» — этот узел требует действия.

Правило для узлов типа LOGIC_OPERATION:

ПолеЗначениеТВОЁ ДЕЙСТВИЕ
usedfalseЛогика НЕ применена в старом графе
commentсодержит «применить»Оператор ТРЕБУЕТ применить эту логику
status"ok"Оператор ПОДТВЕРДИЛ необходимость применения
ВЫВОД:Ты ОБЯЗАН применить эту логику в НОВОМ графе

Пример из реального JSON:

{
  "id": "log_diatopic",
  "name": "Диатопическая",
  "type": "LOGIC_OPERATION",
  "desc": "[МЕТОД] · Не применена",
  "used": false,
  "status": "ok",
  "comment": "Применить!"
}

Значит: Диатопическая логика не была применена, но оператор подтвердил (status: "ok") и написал «Применить!» в комментарии. Ты ОБЯЗАН применить Диатопическую логику в новом графе.

ШАГ 4. ОПРЕДЕЛИ НОВЫЙ СОСТАВ ЛОГИК

Составь список логик для НОВОГО графа:

  • Все логики, которые уже имеют used: true — остаются применёнными.
  • Все логики, которые имеют used: false но comment требует применить — становятся применёнными (used: true).
  • Все остальные логики с used: false — остаются неприменёнными.

ШАГ 5. СГЕНЕРИРУЙ НОВЫЙ ГРАФ

Создай НОВЫЙ HTML-файл с 3Д-сценой. В НОВОМ графе:

  • Все логики из Шага 4 с used: true отображаются зелёным цветом (#60ff90).
  • Все логики с used: false отображаются серым цветом (#444455).
  • Каждая НОВАЯ применённая логика (та, которая была used: false в старом графе) ОБЯЗАНА иметь:
  1. Описание применения в поле desc (что сделала логика, какие противоречия выявила, какие результаты дала).
  2. Входящую связь от CLAIM или EVIDENCE (тип ACTIVATES или INPUT).
  3. Исходящую связь к RESULT или CRITERION (тип FEEDS или DERIVES или VALIDATES).

ЗАПРЕЩЕНО генерировать тот же граф без изменений. НОВЫЙ граф ОБЯЗАН отличаться от старого составом логик и связей.

ШАГ 6. ВЕРИФИКАЦИЯ НОВОГО ГРАФА

Перед выдачей файла проверь:

  • ☐ Каждая применённая логика имеет минимум 2 связи (входящую и исходящую).
  • ☐ Каждая применённая логика имеет описание применения.
  • ☐ Неприменённые логики отображаются серым и скрыты по умолчанию (фильтр).
  • ☐ Число применённых логик в новом графе ≥ числа в старом графе.
  • ☐ Панель узла показывает все 10 полей (императив 5).
  • ☐ Режим выделения работает (императив 6).
  • ☐ Экспорт JSON сохраняет инструкции и комментарии.

3.3. Режим выделения (ОБЯЗАТЕЛЕН)

  1. Чекбокс «Режим выделения» в панели управления.
  2. При включённом режиме клик по узлу добавляет/убирает из выделения.
  3. Выделенные узлы подсвечиваются жёлтым кольцом (RingGeometry, цвет #ffd060).
  4. Счётчик «Выделено: N узлов».
  5. Кнопка «Очистить выделение».

3.4. Создание инструкций (ОБЯЗАТЕЛЬНО)

  1. Кнопка «📝 Создать инструкцию» (активна только при выделенных узлах).
  2. Модальное окно: textarea для текста + select приоритета (HIGH/MEDIUM/LOW).
  3. Отображение выделенных узлов в модальном окне.
  4. После сохранения: инструкция появляется в панели «Инструкции для следующего цикла».
  5. Выделение снимается после создания инструкции.

3.5. Экспорт JSON (ОБЯЗАТЕЛЬНО сохраняет ВСЁ)

Экспортированный JSON ОБЯЗАН содержать:

  • Все узлы с полями: id, name, type, desc, color, pos, status, comment, used.
  • Все связи с полями: from, to, relation.
  • Массив operator_instructions.
  • Метаданные: total_nodes, total_edges, logic_count.

РАЗДЕЛ 5. ПРИМЕРЫ — ПРАВИЛЬНО И НЕПРАВИЛЬНО

5.1. Обработка импортированного JSON

❌ НЕПРАВИЛЬНО (то, что сделал DeepSeek версии 2.1)

Получил JSON с comment: "Применить!" на узлах log_diatopic, log_argumentative, log_nonmonotonic.

Сгенерировал тот же граф на 3 логиках (диалектическая, математическая, формальная).

Проигнорировал инструкции оператора.

Не добавил связей для новых логик.

✅ ПРАВИЛЬНО (то, что ты ДОЛЖЕН сделать)

Получил JSON. Прочитал operator_instructions. Прочитал comment каждого узла.

Обнаружил: log_diatopic (comment: "Применить!"), log_argumentative (comment: "Применить!"), log_nonmonotonic (comment: "Применить!").

Сгенерировал НОВЫЙ граф на 6 логиках: диалектическая, математическая, формальная + диатопическая, аргументационная, немонотонная.

Для каждой новой логики добавил: описание применения, входящую связь от CLAIM, исходящую связь к RESULT.

Обновил панель аудита: «Логика (применено): 6/16».

5.2. Связи для новой логики

❌ НЕПРАВИЛЬНО

Узел log_diatopic существует в графе, но не имеет ни одной связи.

✅ ПРАВИЛЬНО

// Связи для новой диатопической логики:
{ "from": "cl1", "to": "log_diatopic", "relation": "ACTIVATES" }
{ "from": "log_diatopic", "to": "res1", "relation": "FEEDS" }
{ "from": "log_diatopic", "to": "crit3", "relation": "VALIDATES" }

Описание в desc: «Диатопическая логика сопоставила правовую, бухгалтерскую и налоговую системы координат. Обнаружено несогласование требований НК РФ (ст.252) и ФСБУ 5/2019. Сформирована рекомендация по согласованию.»

5.3. Панель узла

❌ НЕПРАВИЛЬНО

Панель показывает только: название, тип, ID. Нет описания, нет комментария, нет трассировки.

✅ ПРАВИЛЬНО

Панель показывает все 10 полей: название, тип, описание, ID, статус, комментарий, вх. связи, исх. связи, трассировка, поле ввода комментария.
